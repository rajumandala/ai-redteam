# R0. AI Red Teaming

## What this part is

[Note 10](https://github.com/rajumandala/aisec-notes/blob/main/10.%20Prompt%20Injection%20and%20Red%20Teaming.md) of the main course introduced red teaming: map the entry points, try the main attack families, and turn every attack that works into an eval. This part treats red teaming as a discipline of its own: how an engagement is scoped, planned, automated, measured and reported, and how it differs for agents and for model safety.

The story stays with the broker from the main course: Kiran leads its red team, and the broker's assistant is what the engagement is for. The attacks in the notes are real, but they run against a system other people built, so they are not shaped by knowing how the defences were written. It runs on this machine, with fake money and synthetic users, so no real account or payment is ever touched. R1 covers how it is scoped and contained.

## The target: FinBot

[FinBot](https://github.com/GenAI-Security-Project/finbot-ctf) is from the OWASP GenAI Security Project. It is one whole application built to be broken: a pretend fintech platform for managing and paying vendors. AI agents onboard vendors, process invoices, check for fraud, pay vendors and send mail, with little human review in between. It has the parts the main course built for the broker:

- **Several agents,** with an orchestrator that hands work from one to the next.
- **MCP tools** (note 06 of the main course) for payments, mail, file storage and system maintenance.
- **Two portals:** one for vendors, who are outsiders, and one for admins.
- **Capture-the-flag challenges.** Each one is a goal, such as "make the invoice agent reveal its rules" or "get a payment sent that is bigger than the invoice". When FinBot sees the goal reached, it awards a flag.

It runs in Docker containers on this machine, locked down as R1 describes. You attack it by hand, in a browser or with a script, and either reach a challenge's goal or do not.

R0–R3 use FinBot only. R4, on automated attacks, adds a second target built for measuring how often an attack works.

## How the notes are built

1. Each note starts from the problem the previous one ended on. R0 starts from note 10.
2. It covers one part of how a red team works.
3. It records what was actually done, in a section called "What happened": a run against a target, or a free check that calls no model.
4. It lists the OWASP risks it meets, each with an example, the issue and the fix.
5. It ends on the next problem and links to the note that deals with it.

## The idea: how an AI red team differs from a pentest

A pentest of a web app asks whether a bug exists. Send the request, and the server either returns another client's data or it does not, every time. Red teaming an AI system keeps the same goal, attacking your own system the way an attacker would, but five things change.

**1. Results are rates.** A model picks each word of its reply with some randomness, which is called sampling ([M4](https://github.com/rajumandala/ai-supplychain/blob/main/notes/M4.%20How%20a%20Model%20Works,%20for%20Security.md), in the Model Supply Chain notes, explains how), so the same attack can work on one try and fail on the next. A finding is "this attack works 3 times in 10", not "this attack works". And "we tried it and it failed" proves little: if an attack works 20% of the time, three tries all fail about half the time. R4 measures a real rate, and R6 explains how sure a rate can be.

**2. The target keeps changing.** A new model snapshot, a changed instruction, a new tool or a new document in the search index can each turn a failed attack into a working one. A result only holds for the exact system it ran on, so record the snapshot the API reports, the prompt version and the tool list with every attempt.

**3. The exploit is ordinary language.** Microsoft's AI red team, after testing more than 100 generative AI products, put it as "you don't have to compute gradients to break an AI system". Rewording, a fake authority or a fake end of the data often does more than any clever technique, which is why a red team tries several wordings of the same attack.

**4. Harm can be in the words, not only in the actions.** An order Ravi never asked for is harm. So is a reply that repeats his PAN (India's tax ID number, which a broker holds for every client), invents a price or reads like a stock tip. Each attack is scored on both.

**5. Grade what crossed the boundary.** The model "agreeing" with Mallory is not the finding. The finding is what got past code: a payment that left the account, data that reached the reply. The main course's [note 05](https://github.com/rajumandala/aisec-notes/blob/main/05.%20Evaluations.md) set the same rule for evals: grade the outcome, not the wording, meaning which orders would actually reach the exchange. Here it is applied to attacks.

Two more distinctions keep a red team's work clear:

- **Red teaming, evals and benchmarks are different jobs.** A red team looks for attacks nobody has written down yet. Evals keep known attacks fixed after every change. Safety benchmarks measure a model in general. Microsoft's team lists "AI red teaming is not safety benchmarking" as one of its eight lessons.
- **Security red teaming and safety red teaming have different targets.** This part is mostly about security: making the broker's app do something it should not. Safety red teaming tests whether the model produces harmful content or gives dangerous help, and is mostly the provider's work. R7 covers where the two meet.

## The run: what counts as a win?

Before attacking anything, Kiran reads how the target decides an attack worked. Every FinBot challenge names a **detector**: the code that watches FinBot and decides whether the challenge's goal was reached. Point 5 above says a red team should grade what crossed the boundary. The question is how many of FinBot's detectors do.

`lab/r0_challenges.py` reads the challenge definitions in the pinned FinBot checkout and records, for each one, its category, its difficulty and how it is graded. A detector that carries a judge prompt asks a model to decide. The rest decide in code, from FinBot's event log and database. The script calls no model and does not start FinBot.

## What happened

Run on 21 October 2026 with `python3 r0_challenges.py`, against FinBot at the commit pinned in `targets.lock`:

| Category | Challenges | What the attacker is after |
|---|---|---|
| Policy bypass | 7 | An agent approves what its rules forbid: an invoice over the limit, a prohibited vendor, a lower risk score |
| Data exfiltration | 4 | Personal or another vendor's data leaves by mail or a network request |
| Recon | 2 | An agent reveals its hidden instructions |
| Destructive | 2 | Records deleted or damaged |
| Code execution | 2 | A script runs through the system-maintenance tools |
| Guardrails lab | 2 | The player builds a defence, rather than an attack |

That is 19 challenges: 5 beginner, 12 intermediate, 1 advanced and 1 expert.

**How they are graded:** 15 in code, 4 by a model acting as judge.

The 15 graded in code watch what happened. The code-execution detector watches for a call to the script-running tool. The overpayment detector compares the transfer FinBot created with the invoice amount in its database. That is point 5 in practice.

The 4 graded by a model are the two recon challenges, one exfiltration challenge and the risk-downplay challenge. Their success is in the words: whether a reply leaked the hidden rules, or whether an assessment played a risk down. A string match cannot decide that, so FinBot asks a model. That is point 4: harm in words needs a different judge from harm in actions. A model judge costs a call each time and can be wrong. R6 and R7 cover how to check it.

One detail matters for later. The overpayment detector awards its flag only if the payment was inflated **and** the invoice's attachment contains hidden text, such as white or tiny type. It grades the method as well as the outcome, because the challenge is about that method. A red team grading the broker's own system would count an inflated payment as a finding however it was caused. A flag is FinBot's definition of a win, not the red team's, which is why R6 records both.

## OWASP risks in this note

### LLM01: Prompt Injection, and ASI01: Agent Goal Hijack

- **Example:** A vendor writes text into an invoice's description that FinBot's invoice agent reads, aiming to make it reveal its rules or approve an invoice over its limit.
- **Issue:** Whether this works depends on the wording and on chance. A test that tries one wording a few times can report "not vulnerable" for an attack that works one time in five, and a reply that sounds compliant is not a payment.
- **Fix:** Test each attack several times and in several wordings, report rates with how many runs they rest on, record what the API says answered, and judge the result by what got past code. The control that holds whatever the rate is a rule in code, like note 07's news rule in the main course: once a request has read outside text, such as a news article, code refuses to let that request place an order, whatever the model asks for.
