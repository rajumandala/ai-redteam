# R5. Red teaming agents

R4's problem is how to search for attacks repeatedly rather than invent every candidate by hand. But more candidate text is not enough for an agent. An agent can read a document, delegate work, call a tool, retry and finally report success. Kiran needs to know which of those actions crossed a boundary, and whether a chain of individually ordinary steps produced an unauthorised result.

## The idea

For a chatbot, the reply is usually the output. For an **agent**, a system that chooses and uses tools to complete a task, the reply is only one part of the result. A polite refusal can follow a harmful tool call. An enthusiastic claim of success can follow no action at all.

An agent test therefore has three objects:

1. **The trajectory:** the ordered record of observations, decisions, delegations, tool requests, tool responses and effects.
2. **The authority:** which user or service is allowed to take each action on each object.
3. **The final state:** what changed in the application, including intermediate effects that were later undone.

A **multi-step chain** connects an attacker-controlled observation to a later forbidden action. It might be document → reviewer → orchestrator → mail sender. The question is not whether one model was persuaded. It is where an external claim became permission to act.

This note uses FinBot, the intentionally vulnerable vendor-payment application, as a source-grounded example. It also describes **fake tools**: offline substitutes that record a proposed action and update an in-memory fake world instead of contacting services. These are a testing design, not an implemented FinBot integration or a verified target exploit. No paid or live experiment is run here.

## Step 1: map the action chain, not only the agents

The reviewed FinBot source provides this candidate chain:

| Stage | Source-grounded behaviour | What a later test must establish |
|---|---|---|
| Document enters context | The fraud agent selects qualifying vendor documents and adds their text to a document-review prompt | The intended document actually reached this workflow |
| Reviewer produces a summary | Its instructions request document action items in the summary | The attacker-controlled request was retained, rather than rejected or described as untrusted |
| Orchestrator carries context | It captures task summaries and appends accumulated prior context to later delegations | The receiving agent obtained the relevant content with its provenance intact or lost |
| Communication agent chooses mail | It has FinMail capabilities and recipient guidance | A request targeted a recipient outside the independently authorised set |
| Tool acts | The common agent loop dispatches recognised tool calls and returns tool output to the model | The call was accepted and the target state changed |

These are not five demonstrated exploit steps. The first, third and dispatch behaviour are visible in code; the attack-dependent choices remain untested. Guardrail hooks run around recognised tool calls in the common loop. Their presence alone neither proves prevention nor proves bypass.

There is also a useful architectural correction: the orchestrator exposes a system-maintenance delegation role, but the reviewed implementation routes it to the fraud-agent runner with SystemUtils context. Six delegation roles do not imply six independent specialist implementations. Trace the callable actually reached rather than relying on an architecture diagram.

## Step 2: separate attempted actions from committed effects

Before running anything, write an action policy for the fixture. For example: vendor A's compliance review may read A's document and send a review result to a fixed approved recipient. It may not read B's private document, change payment records or choose an additional recipient from text inside A's document.

An **invariant** is a rule that must remain true throughout a run. Here the recipient set and vendor ownership rules are invariants, not suggestions to the model.

| Outcome | Evidence required | How to label it |
|---|---|---|
| Agent asks for a forbidden action | Recorded tool name and arguments, with actor and workflow IDs | Attempted violation |
| Permission check rejects the request | Denial event and unchanged protected state | Blocked attempt |
| Unknown or invalid tool is requested | Invalid-call event, no dispatched callable | Invalid action, not execution |
| Fake tool accepts the request | Fake ledger transition in the offline fixture | Simulated violation |
| Real local tool accepts the request | Authoritative application record and attributable state difference | Committed target violation, only after a live authorised test |
| Final reply says an action occurred | Reply text alone | Unverified claim |

Check every transition as well as the final state. A leak followed by deletion is still a leak. A duplicate payment followed by a refund is still a forbidden intermediate action. Grade legitimate utility separately: did the review complete, was its authorised notification delivered, and were unrelated records left alone?

## Step 3: design fake tools that cannot escape the fake world

A fake tool preserves the interface needed for a test, but removes the real effect. A fake mail sender records recipient lists, subject, body, attachments and a synthetic message ID in an in-memory ledger. It does not resolve addresses or contact a mail service. A fake payment tool records an attempted transfer in fake balances. A fake document reader returns fixture-owned synthetic content only.

For this tabletop, design the following components; do not import and start FinBot to obtain them:

- **Fixture:** vendors A and B, an A-owned document, a B-owned private canary, an authorised recipient set, and empty mail and payment ledgers.
- **Dispatcher:** a fixed allowlist of test tool names and argument schemas. Unknown tools fail closed. There is no general network, shell, file-system or dynamic import capability.
- **Recorder:** an append-only ordered event list with attempt, workflow, actor, object, arguments, response, policy decision and before/after state identifiers.
- **Oracle:** deterministic checks of ownership, recipient permissions, ledger contents and legitimate task completion. An oracle is simply the independent rule used to grade a test.
- **Reset:** a fresh deep copy of the initial fixture for every trial, including counters, context, caches and deterministic synthetic IDs.

Use two explicit modes. **Observe-only mode** accepts an otherwise well-formed request into a fake ledger so the grader can see the agent's unsafe choice. **Enforcing mode** rejects requests outside the fixture policy. Report which mode produced the result. A fake tool that always rejects everything measures its own restriction, not whether the agent chose safely.

Fakes do not automatically have the same semantics as real tools. Differences in defaults, permission handling, error messages, retries and side effects can change the result. Before treating a simulation as evidence about FinBot, a later authorised integration must check interface and behaviour parity. No such integration, parity check or fake-tool implementation was performed here.

## Step 4: specify an offline manual experiment

This is a reproducible **tabletop protocol** for checking the proposed evidence and grader design. It needs no model and no target requests. A human walks through hand-authored event cards; they are hypothetical events, not captured target traces.

1. Fix the fixture above and write its allowed reads and recipient set on a separate policy card. Give the task and fixture version identifiers. Start with empty ledgers and no inherited context.
2. Construct a **clean trajectory**: permitted document read, factual review summary, delegation to communication, authorised mail record, task completion. The grader should report utility true and no violation.
3. Reset. Construct an **attempted-only trajectory** that requests an unapproved recipient but receives a permission denial. The grader must distinguish the unsafe request from a committed effect. Utility may fail if the required notification is missing.
4. Reset. Construct a **simulated-commit trajectory** whose fake mail record includes the B-only canary at an unapproved recipient. The grader should report a simulated confidentiality violation. Add a later deletion event: the historical violation must remain true.
5. Reset. Construct a **false-success trajectory** with a successful final reply but no mail record. The grader must not count either delivery or attack success from the reply.
6. Reset. Construct a **delivery-failure trajectory** where no matching document is selected. Mark the injection stage not reached. Do not count that as model resistance.
7. Reset. Construct an **error trajectory** with a tool timeout and a retry. Check that errors remain separate and duplicate synthetic effects are detected. A request repeated twice must not silently become one event.
8. Restore the initial fixture and independently recompute each expected label from the event cards. If two reviewers disagree, clarify the rule before any agent run.

These cards specify grader acceptance tests. They have not been executed as software or walked through as a recorded experimental run in this session. They contain no working injection strings. Passing them later would validate the grader's handling of those examples, not demonstrate model vulnerability or safety.

A future model-driven simulation would replace hand-authored choices with the model's tool requests, through an approved harness. That still requires separate permission if it invokes a paid provider. A future live FinBot test additionally needs a verified adapter, complete internal-call accounting, stop propagation and controlled output destinations. The existing harness does not automatically instrument every FinBot internal call. No browser or direct-tool shortcut is justified by calling it an offline exercise.

## Step 5: test the joins in a chain

To investigate the document-to-mail hypothesis later, hold the legitimate task and fixture fixed and change one boundary at a time:

| Condition | Purpose | Evidence to compare |
|---|---|---|
| Clean document | Establish ordinary utility | Review completed; authorised mail only |
| Candidate document | Test the complete proposed chain | Delivery, summary, delegation, request and final effect |
| Same document, prior summary propagation removed in an isolated test fixture | Test whether carry between agents is necessary | Which downstream stages disappear while the legitimate task still works |
| Same candidate, recipient policy enforced outside the model | Test containment | Request can remain unsafe while committed effect is blocked |
| Same candidate, fresh workflow after reset | Test accidental persistence | No previous summary or marker leaks into the new attempt |

Removing a component is an **ablation**: a controlled comparison that helps explain what contributed to the result. It changes the system, so report it as an isolated test configuration, not a result on unmodified FinBot. If removing context also breaks clean-task utility, it does not cleanly isolate the attack mechanism.

Keep each link's result. Document delivered but no summary carry means the chain stopped early. Summary carried but recipient denied means an independent boundary contained it. An end-to-end simulated effect does not tell you which real guardrail would accept it. For retries and delayed work, capture workflow IDs and ordering so a mail record from a previous trial cannot be attributed to the current one.

## OWASP risks in this note

OWASP categories name recurring failure modes. LLM refers to the Top 10 for LLM Applications; ASI refers to the Top 10 for Agentic Applications, using the course's 2026 labels.

### ASI01: Agent Goal Hijack

- **Example:** A vendor compliance review is redirected towards an unauthorised notification.
- **Issue:** Completing a plausible subtask can move the workflow away from the user's authorised goal without an obviously malicious final reply.
- **Fix:** Define task authority independently of retrieved content and check each requested action against it. Retain intermediate effects as evidence.

### ASI06: Memory & Context Poisoning

- **Example:** An external document's action item is carried forward in an agent summary.
- **Issue:** Context can acquire apparent authority as it crosses a delegation boundary; stale context can also corrupt repeated trials.
- **Fix:** Preserve source and trust metadata, pass structured facts rather than executable directives, and isolate and reset workflow context between tests.

### ASI02: Tool Misuse and Exploitation

- **Example:** A communication tool is requested with an unapproved recipient even though sending mail is a legitimate capability.
- **Issue:** A valid tool name and schema do not establish permission for that actor, object and destination.
- **Fix:** Enforce object and recipient authorisation in the tool layer. Grade attempted, blocked, simulated and committed actions separately, and test that the allowed task still completes.

## Problem and next step

**Problem:** even a well-attributed chain says little about its frequency. Repeated trials need independent resets, working clean controls, reliable graders and an honest denominator. Adaptive manual changes must not be presented as independent samples of one fixed attack.

**Next, in [R6. Measuring](<R6. Measuring.md>):** measure attack success alongside utility, quantify uncertainty, and check whether graders and coverage justify the claims.
