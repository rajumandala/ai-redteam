# R1. Scope and Rules of Engagement

R0 ended with Kiran ready to attack the real assistant. An attack that works there can place real orders, show a real client's data, run up the model bill, and look to the security operations team exactly like Mallory.

## The idea

A pentest starts with rules of engagement: who approved it, what is in scope, when it runs, and what makes the testers stop. An AI red team needs the same document, plus a few rules a web pentest never needed, because the AI system has more parties in it and its outputs can be harmful in themselves.

The rules only help if they are enforced. So in this part every attack goes through a harness, `lab/src/redteam/harness.py`, that reads the engagement file and refuses anything outside it. A tester who mistypes a URL gets an error, not an attack on someone else's system.

```toml
id = "RT-2026-001"
tester = "kiran"
authorised_by = "Head of security, ticket SEC-1432"   # empty means no attack runs
expires = "2026-11-30"
stop_file = "STOP"            # create it to halt the engagement at the next model call
results_dir = "results"       # gitignored; files are readable by the tester only

[scope]
environments = ["agentdojo", "finbot-local"]
urls = ["http://127.0.0.1:8000"]              # the local FinBot; the hosted CTF is someone else's system
models = ["gpt-6.1-sol"]

[budget]
max_calls = 300
max_tokens = 1500000

[data]
canaries = []                 # planted fake values that may appear without stopping the run
stop_patterns = { "an API key" = "sk-[A-Za-z0-9_-]{20,}", "a private key" = "-----BEGIN [A-Z ]*PRIVATE KEY-----" }
```

## Step 1: written authorisation

Someone with the authority to accept the risk signs off, in writing, before anything is sent: here the head of security, through a ticket. The authorisation names the scope below, the dates, the contacts on both sides, and the stop conditions in Step 4. It ends on a date. An engagement that drifts on for months after its approval is no longer approved.

The harness checks both: no `authorised_by`, no attack, and after `expires` every call is refused.

## Step 2: what is in scope

An AI system has more layers than a web app, and each one needs a yes or no:

| Layer | In scope here? | Why |
|---|---|---|
| The broker's app, instructions and tools | Yes | This is what the engagement is for |
| The broker's own MCP server, search index and memory store | Yes | The broker runs them |
| A vendor's MCP server or another company's agent | No. Simulated instead | Attacking another company's system needs its agreement. Note 06 tested a malicious vendor by writing one in the lab, which tests the broker's controls without touching the vendor |
| The hosted model itself | Only as part of the app | The provider's terms and abuse monitoring apply, see below |
| Real clients' accounts | No | Synthetic test accounts only |

The model provider needs its own line. Attacks sent to a hosted model pass through the provider's abuse monitoring ([M3](https://github.com/rajumandala/ai-supplychain/blob/main/notes/M3.%20Model%20Providers%20and%20Provenance.md)). Microsoft's documentation for its hosted models says recurring jailbreak attempts make a high abuse score more likely, and that confirmed abuse can lead to suspension of access. A red team that runs hundreds of jailbreaks from the production account can get the production assistant cut off. So run attacks from a separate account or project, read the provider's usage policies for what testing they allow, and use the provider's own route for red teaming if it has one.

## Step 3: where to test

Most attacks belong in a copy of the system, not in production:

- **A lab copy** with the real instructions, tools and checks, but fake money and synthetic users. Here an attack can "send" a thousand payments and nothing happens. This part's lab uses two copies that other people built, so the attacks are not shaped by knowing how the defences were written: AgentDojo's simulated banking, Slack, travel and workspace agents, and OWASP's FinBot, a deliberately vulnerable vendor-management platform, run on this machine.
- **Synthetic data with canaries.** Plant fake values that exist nowhere else, such as a fake client ID or a fake key, in the test data. If one appears in a reply, a log or a vendor's request, the leak is found with a string match, without guessing what counts as sensitive.
- **Production, only for what needs it**, such as checking the real configuration, the real network path or the real monitoring. Then use test accounts with no money in them, limits far below normal ones, and the same harness.

The harness refuses any environment except the two lab ones, and any URL except the local FinBot. FinBot also runs as a public CTF on the internet. That copy is out of scope: it belongs to someone else, other people are playing on it, and their data and the organisers' bill are not this engagement's to risk.

A lab copy that is built to be broken is a risk of its own. FinBot has challenges that end in running code on its server, and it holds a real API key so its agents can call a model. So the lab is set up as untrusted code:

- **Pinned.** Both targets are fixed to exact commits in `targets.lock`, read before they run, and kept out of this repo. An update to a target is a new version to review, not something pulled on the next run.
- **Contained.** `lab/finbot/up.sh` runs FinBot in a container that listens on this machine only, with every Linux capability dropped, no way to gain privileges, and limits on memory and processes. Its Redis is not reachable from outside the container network at all.
- **A key of its own.** FinBot gets a separate key, from a separate project with a spending limit. Anyone who wins the code-running challenges can read it, and that should cost a small, capped amount.## Step 4: budgets and stop conditions

A red team's own traffic can be the denial of service. Automated attacks (R4) send thousands of requests, and an agent that loops calls the model until something stops it. The engagement sets a call budget and a token budget, and the harness checks them before every model call, not after the run. A call is counted when it is sent, so calls that fail still use the budget.

The harness only sees the calls it sends. When the target is a whole application, like FinBot, the application calls the model itself, from its own server, and one request from the tester can start many model calls. For those, the budget is the spending limit on the target's own project, set before the engagement starts.

Testers also need a way to stop at once, and conditions that mean they must:

- **A stop file.** Creating `lab/STOP` halts the engagement at the next model call, whatever script is running.
- **A real secret appears.** The harness stops if a transcript contains something shaped like an API key or a private key that is not one of the planted canaries, and does not write that line. In a lab with only synthetic data, a real secret means the lab is not as isolated as everyone thought, and the key must be rotated before the run goes on.
- **A real side effect.** An order or message that reached a real system.
- **A warning from the provider**, such as an abuse-monitoring email. Stop and talk to them before carrying on.

## Step 5: deconfliction

From the outside, Kiran's attacks look exactly like Mallory's. The monitoring from [note 14](https://github.com/rajumandala/aisec-notes/blob/main/14.%20Architecture%20Review.md) should alert on them, and the security operations team should not spend a night chasing them. So every request carries the engagement ID, here in the request's metadata, and the operations team knows the engagement's ID and dates.

Knowing who is testing does not mean being told what is tested. If the alerts are part of the test, the operations team is told only that an engagement is running, and the report checks which attacks were detected and how fast.

## Step 6: handling what the red team finds

The transcripts are sensitive in two ways. They hold working attacks against the broker's assistant, and some hold harmful text that a successful jailbreak produced. So:

- Transcripts stay in `lab/results/`, which is gitignored, in files only the tester can read (mode 600).
- Tickets and chat messages describe a finding and point to the transcript line by its hash. They do not paste the attack or the harmful output.
- The transcripts have an end date for deletion, set in the authorisation.
- Each line records the engagement, the tester, the time and the model snapshot that answered, so the finding can be reproduced later (R8).

## What happened

`lab/r1_checks.py` checks that the harness enforces these rules. It uses a stub model, so no API call is made. All 28 checks passed on 21 October 2026:

| Rule | Check |
|---|---|
| Authorisation | No `authorised_by` is refused; a date after `expires` is refused |
| Scope | `production` and an unlisted model are refused. The local FinBot is allowed; the hosted CTF and another port on this machine are refused |
| Budget | A stub model that calls a tool forever, inside AgentDojo's real agent loop on the banking bill task, was stopped by the call budget after exactly 3 calls |
| Stop file | After `STOP` was created, the next call was refused and none was sent |
| Canaries and secrets | A planted canary key in a reply was recorded. A key-shaped value that was not a canary stopped the engagement, and its line was not written |
| Transcripts | The file was mode 600, its folder 700, every line had the engagement ID and tester, and `lab/results` is gitignored |
| Deconfliction | The request sent to the model carried `metadata: {"red_team_engagement": "RT-2026-001"}` and `store: false` |
| Containment | FinBot listened on 127.0.0.1 only, its Redis was not published, and both containers dropped every capability, could not gain privileges and had a memory limit |

Building the lab found one problem the checks now cover. AgentDojo's own model wrapper retries a failed call up to three times, whatever the error. A stop from the harness is an error to it, so it would have been retried. The lab's agent calls the model through the harness instead, and the budget check above runs through AgentDojo's real loop to prove it.

These checks test the harness, not the provider. Whether the provider records the metadata in a place the operations team can see depends on the provider and on the company's own logging.

## OWASP risks in this note

### LLM06: Unbounded Consumption

- **Example:** An automated attack, or an agent stuck in a loop, sends model calls until someone notices the bill.
- **Issue:** The red team becomes the denial of service, against the broker's budget and its rate limits.
- **Fix:** A call budget and a token budget, checked by the harness before every call, a spending limit on the project of any target that calls the model itself, and a stop file that works at once. In the run, the budget stopped a looping agent after 3 calls.

### LLM02: Sensitive Information Disclosure

- **Example:** A successful attack makes the target print the API key it uses, and the tester pastes the transcript into a ticket.
- **Issue:** The red team spreads the secret it found, and a real secret in a lab shows the lab was never isolated.
- **Fix:** Synthetic data with planted canaries, a stop condition for any key-shaped value that is not a canary, a separate capped key for the target, and transcripts kept private and referenced by hash.

### ASI02: Tool Misuse and Exploitation

- **Example:** An injection test run against production makes the agent send a real payment.
- **Issue:** A test that succeeds has a real effect, on a real account.
- **Fix:** Attack a lab copy with fake money; in production, only test accounts with limits far below normal; and stop at once on any real side effect.

### ASI05: Unexpected Code Execution

- **Example:** A tester wins FinBot's code-running challenge, and the code runs on the tester's laptop with access to their files and keys.
- **Issue:** A target built to be broken is untrusted code, and the red team runs it.
- **Fix:** Pin the target to a reviewed commit, and run it in a container reachable from this machine only, with no capabilities, no privilege gain and resource limits.

## Problem and next step

**Problem:** Kiran now knows where the red team may attack and how to stop safely. But the scope says nothing about what to try. A list of famous jailbreaks finds famous jailbreaks, and may never touch the paths in this assistant where an attack would actually hurt.
