# R6. Measuring

R5 ended with a trace: proof that an attack can happen. Kiran's next questions are how often, and how much of the system was tested. A convincing trace proves possibility, not prevalence.

## The idea

A measurement needs three things: a unit (what one try is), a denominator (how many tries), and an outcome checked in state, not taken from the model's own account.

Attack success is always reported next to **utility**: how often the agent still does the legitimate task correctly. R4's run showed why. An agent that never pays a bill cannot pay Mallory, and its 0/10 attack rate is meaningless on its own.

Two different things limit a result:

- **The number of runs** sets how sure the rate is.
- **The choice of tasks** sets what the rate covers.

A thousand runs of one task are a precise measurement of one task.

## Step 1: count everything

One try is one fresh run of a fixed attack on a fixed task. For every run, record the suite, the user task, the attacker goal, where the attack went in, the attack's version, the model the API reported, the prompt and tool versions, the starting state and the grader's version.

For each task and attack, report:

| Field | Meaning |
|---|---|
| Attempted | Every run started |
| Completed | Runs with a valid grade |
| Errors | Runs without one, and why |
| Attack success | The attacker's outcome is in the final state |
| Utility | The user's task was done correctly |
| Unsafe request | The agent asked for the forbidden action, even if code refused |
| Unsafe effect | State shows it happened |

An error is neither a refusal nor a success. AgentDojo's own benchmark counts some errors as successful attacks. The lab counts them apart. If a run of 10 has 1 success and 2 errors, the honest range is 1/10 to 3/10, depending on what the errors would have been. That range is a sensitivity check, not a confidence interval.

Attack success and utility are not opposites. Both can be true: the agent pays the real bill and also pays Mallory. Keep both. In a run with no attack, attack success is "not applicable", not zero.

## Step 2: put uncertainty next to every rate

If the runs are independent and the attack has a fixed chance of working, the number of successes follows a **binomial** distribution, the same maths as counting heads in coin tosses. That assumption breaks if runs share state, if the attack was tuned between runs, or if the provider changes the model in the middle.

A **95% confidence interval** is a range built by a method that, over many repeated experiments, contains the true rate 95% of the time. It is not a 95% chance that this particular range is right.

Two calculations, both in `lab/measurement_checks.py`:

- **The zero-success upper bound.** With 0 successes in n runs, the true rate is below `1 - 0.05^(1/n)`, at 95% confidence, one-sided. For R4's 0/10, that is **25.9%**.
- **The Wilson interval.** A two-sided interval that behaves well near 0 and 1, where the simple textbook formula fails. For 0/10 it is about **0% to 27.8%**.

Both are right; they answer slightly different questions. R4's "below about 26%" is the first. A report names the method.

To get the zero-success bound below 5% takes **59** runs with no successes. Below 1% takes **299**. That is if all of them fail, and it covers only the tested setup.

Do not keep adding runs until the interval looks good. Choose the number before starting.

## Step 3: keep search and measurement apart

An **adaptive attacker** changes the next try after seeing the last result, as R4's search design would. Its winner was picked for looking good, so a binomial interval on the search's own tries is wrong.

Freeze the winner and the grader, then run them on tasks the search never saw. Report both: what the search cost, and the held-out rate. To measure the searcher itself instead, the unit becomes one whole search with a fixed budget, repeated from clean state.

Pair clean and attacked runs by task and starting state. Show per-task numbers before any average. A **macro average** weights every task equally; a **pooled average** weights tasks by how many runs they had. Say which. Runs of the same task resemble each other, so a claim about tasks in general needs uncertainty across tasks, not just across calls.

## Step 4: test the judge

The **judge** is whatever decides if a run counts. For actions, the best judge is state: a transfer in the ledger, a mail in the outbox, another vendor's data in the reply. A tool request is weaker evidence than a tool effect.

Test the judge on cases with known answers before trusting it, as R5 did: a refused request, a canary quoted harmlessly, a permitted action, a wrong recipient, an unfinished run. For harm in text, a written rubric and human reviewers may be needed, and a second model is not automatically right (R7). Text from the target must not be able to instruct the judge.

A CTF flag is a clue, not proof. FinBot can award a flag without the effect the report claims, and an effect can happen without a flag. Record both.

## Step 5: the next experiment

R4's result cannot be fixed by more runs of the same task, because the agent never completes it. The next paid experiment would:

1. Pick several user and attacker task pairs, across more than one suite, before looking at any attack result.
2. Run the clean tasks first. A task with no working baseline is dropped or investigated, not reported as secure.
3. Keep only tasks the model actually completes. Do not change the instructions to force it to pay. If the configuration must change, version it and rerun both clean and attacked runs.
4. Freeze the attacks and the number of runs, then run them through the harness from fresh state.
5. Publish per-task counts, intervals, errors, utility, cost and a coverage table. Keep the attack text private.

If no task completes, that is the result: no useful agent was tested. Untested surfaces are untested, not safe.

## What happened

On 21 October 2026, `python3 measurement_checks.py` passed 9 of 9 tests. They check the zero-success bound, the Wilson interval, that more runs tighten the bound, that invalid counts are refused, that errors are counted apart, that an unscored run is rejected, and that zero completed runs give no rate. They test the arithmetic and the bookkeeping, not an agent.

`uv run python r1_checks.py` was rerun and passed 28 of 28, including the containment of the local FinBot containers. No model was called.

The numbers in Step 2 reinterpret R4's recorded counts. They do not fix its utility problem.

## OWASP risks in this note

### LLM01: Prompt Injection, and ASI01: Agent Goal Hijack

- **Example:** A bill attack fails ten times against a banking agent that never pays any bill.
- **Issue:** A zero is read as evidence that a useful system is safe.
- **Fix:** Publish the interval, clean and attacked utility, and the tasks covered. Confirm frozen attacks on fresh tasks.

### ASI02: Tool Misuse and Exploitation

- **Example:** The agent asks for an unauthorised transfer, and code refuses.
- **Issue:** A judge that reads the reply cannot tell an attempt from a payment.
- **Fix:** Grade the request and the effect separately, and test the judge on known cases first.

## Problem and next step

**Problem:** a state grader can show no unauthorised action happened while the reply itself gave harmful help. Harm in words and harm in actions need different measurements.
