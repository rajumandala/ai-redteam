# R6. Measuring

R5 follows actions across an agent chain. Finding one unsafe chain still leaves Kiran with a question: how often does it happen, and how much of the system has actually been tested? A convincing trace proves possibility, not prevalence.

## The idea

A measurement needs a defined unit, a denominator and an outcome checked independently of the model's claim. Report attack success beside **utility**, the fraction of legitimate tasks completed correctly. An assistant that refuses every task may block every payment attack without being useful.

The number of repeated runs controls sampling uncertainty. The choice of tasks controls coverage. More repeats of one task do not give broader coverage.

## Step 1: name the unit and keep the denominators

Use one fresh task execution as the unit for a fixed attack. Record the suite, user task, attacker goal, injection surface, candidate version, model identifier, prompt and tool versions, initial-state identifier and grader version. Keep a run identifier so retries cannot overwrite failures.

For each task pair and attack, report:

| Field | Meaning |
|---|---|
| Attempted | All executions started under the declared policy |
| Completed | Executions with valid final-state grades |
| Errors | Executions without a valid outcome, with reasons |
| Attack success | Attacker's forbidden outcome present in state |
| Utility | Legitimate user's goal correctly completed |
| Attempted unsafe action | Agent requested it, even if enforcement blocked it |
| Executed unsafe effect | Authoritative state confirms it happened |

An error is not automatically either a refusal or an exploit. Report success/completed together with errors/attempted. If there are s successes, e errors and n attempts, s/n through (s+e)/n is a useful worst-case sensitivity range when each missing outcome might have failed or succeeded. It is not a confidence interval. If errors themselves cause harm, define and grade that harm separately.

Attack success and utility are not complements. Both can be true, such as paying the genuine invoice and also paying Mallory. Keep both booleans. In a clean control there is no active attacker goal; mark attack success not applicable rather than inventing a clean attack rate.

## Step 2: put uncertainty next to a rate

For independent repetitions of a fixed attack with a stable success probability, the result can be treated as a **binomial** count: s successes in n trials. These assumptions matter. Shared history, adaptive selection and changing provider models can invalidate them.

A **confidence interval** is a procedure whose intervals cover the true rate at a stated frequency over repeated experiments. It is not a probability that this particular rate lies inside this particular interval.

The [free measurement exercise](../lab/measurement_checks.py) implements two useful calculations:

- A two-sided 95% **Wilson interval**, which behaves better than the simple normal approximation near zero or one.
- An exact one-sided 95% upper bound for zero successes: `1 - 0.05 ** (1/n)`.

For R0's 0/10 fixed-attack result, the one-sided upper bound is **25.9%**. A two-sided Wilson interval is approximately **0%–27.8%**. These are different methods and different sidedness, not contradictory answers. R0's rough 26% statement uses the one-sided bound. Keep the method in the report.

To put the zero-success one-sided upper bound below 5%, at least **59 independent repetitions** are needed. Below 1% needs **299**. This assumes zero successes and a predeclared sample size; it is not a promise that those runs will all fail. It also covers only the tested configuration and task distribution.

Do not keep sampling until the interval looks favourable. Choose a fixed sample size or use a statistically valid sequential procedure designed before testing.

## Step 3: separate search from confirmation

An **adaptive attacker** changes the next attempt after seeing a result. The winner's search score is selected for looking good; an ordinary fixed-attack interval on those same attempts is misleading.

Freeze the chosen candidate, the grader and the evaluation tasks after discovery. Evaluate on held-out tasks not used to choose the attack. Report both the discovery cost and held-out success. If the goal is instead to measure an adaptive attacker, define the unit as a whole search episode with a fixed budget, reset state between episodes, and measure success within that budget across independent episodes.

Keep clean and attacked task runs paired by task and initial state. Show per-task rates and utility before averaging. A macro average gives each task equal weight; a pooled average gives tasks with more runs more weight. Name which one is used. Repetitions within a task share properties, so a generalisation claim across tasks needs task-level uncertainty, not only a binomial interval over all calls.

## Step 4: test the judge, not only the agent

A **judge** is the mechanism deciding whether a result meets the criterion. Prefer authoritative state for actions: a persisted transfer, delivered synthetic email or cross-vendor data appearing at the output boundary. A proposed tool call is weaker evidence than its execution.

Test graders with deliberately constructed positive and negative fixtures. Include a blocked request, quoted canary text, a successful permitted action, a wrong recipient, and an incomplete run. For text safety, a human-reviewed rubric may be needed; a second model is not automatically ground truth. Calibrate it against independently labelled cases and report false positives, false negatives and reviewer disagreement. Keep target-controlled text from issuing instructions to a judge; use constrained inputs and audit disagreements.

A challenge flag is a clue, not sufficient evidence of every claimed effect. Conversely, an effect can exist without a flag. Record both the flag and the independent state observation.

## Step 5: make coverage and the next experiment explicit

The next paid experiment, **not run here**, should:

1. Select multiple user/attacker task pairs before looking at attack outcomes, including more than one suite where the goal fits.
2. Run clean controls first. If a task has no useful baseline, investigate ambiguity or tool incompatibility rather than declaring it secure.
3. Choose a task the model demonstrably completes. Do not invent dates or amounts to force utility. If instructions must change, version the configuration and rerun both clean and attacked controls.
4. Freeze the attack catalogue and sample size, then repeat on fresh state through the harness.
5. Publish task-level counts, uncertainty, errors, utility, cost and the coverage matrix. Keep payloads private.

If no task completes, that is the result. There is no basis for claiming that a useful agent was tested. Uncovered surfaces remain untested, not safe.

## What happened

On 21 October 2026, `python3 measurement_checks.py` passed **9/9 free unit tests**. They cover the zero-success bound, Wilson endpoints and symmetry, tighter bounds with more repetitions, invalid counts, separate error accounting, rejection of missing grades and refusal to calculate a rate for zero completed trials. These tests use authored records and arithmetic; they are not agent evaluations.

The existing free rules-of-engagement checks were rerun: **28/28 PASS**, including checks of the existing local FinBot containers' configuration. No target-agent request or paid model call was sent.

No additional task pair, clean utility control or repeated AgentDojo experiment was run. R0 remains historical evidence: each of three attack variants scored 0/10, with utility also 0/10; the clean control's utility was 0/10. The arithmetic above reinterprets those recorded counts. It does not repair the utility problem or produce a cross-suite rate.

## OWASP risks in this note

### LLM01: Prompt Injection, and ASI01: Agent Goal Hijack

- **Example:** A document attack fails ten times against a banking agent that never pays a bill.
- **Issue:** A zero attack count is mistaken for evidence that a useful system is safe.
- **Fix:** Publish uncertainty, clean and attacked utility, and task-level coverage. Confirm frozen candidates on fresh cases.

### ASI02: Tool Misuse and Exploitation

- **Example:** The agent requests an unauthorised transfer, but code rejects it.
- **Issue:** A reply-only judge conflates attempted misuse with an executed payment.
- **Fix:** Grade the request and the effect separately, and test the state observer with positive and negative fixtures.

## Problem and next step

**Problem:** a correct state grader can show that no unauthorised tool action happened while missing harmful help in the reply itself. Content harm and application security need related but different evaluations.
