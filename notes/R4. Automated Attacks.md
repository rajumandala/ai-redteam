# R4. Automated Attacks

R3 ended with a few attacks written by hand, one wording at a time. Kiran cannot try hundreds of wordings, document layouts and tool results that way. Code can. It can also repeat the same mistake a thousand times, against the wrong system, at the broker's expense.

## The idea

Automation does two different jobs, and mixing them up is the commonest error in AI red-team reports:

- **Discovery** finds attacks. The tester, or a program, changes the next attempt after seeing the last result.
- **Evaluation** measures them. A fixed attack, chosen before the test, runs on fresh cases.

The best score from a discovery run is not a success rate. It is the best of many tries, picked because it looked good. Only a frozen attack, run on cases it was not tuned on, gives a rate.

Two terms used below:

- A **scanner** is a program that sends a collection of known attacks and reports which ones got through.
- An **attacker model** is a language model asked to write or rewrite attacks against the target.

Neither replaces R1's rules or R3's grader. The scanner sends; the harness decides whether it may; the grader decides whether anything crossed the boundary.

## Step 1: choose a method

| Method | What changes | What it needs | Main limit |
|---|---|---|---|
| Fixed catalogue | Known attack families and placements | Approved inputs to the app | Misses anything new |
| Attacker-model search | Wording, rewritten after each reply | A second model, in scope, with its own budget | Costs calls; can overfit to one task |
| Gradient search | Individual tokens, chosen by maths on the model's insides | The model's weights | Only works on open models; may not transfer |
| Workflow scanner | Inputs, tool results and conversation steps | An adapter for the app and a way to read its state | Can test a route the real app never exposes |

The well-known examples, so the names are familiar:

- **GCG** (Greedy Coordinate Gradient, Zou et al., 2023) is gradient search. It uses the model's gradients, which say how each token in the input pushes the output, to find a string of odd tokens that makes an open model comply. A hosted API does not expose gradients, so it is run on an open model and the result is tried on the hosted one.
- **PAIR** (Prompt Automatic Iterative Refinement, Chao et al., 2023) is attacker-model search. One model writes a jailbreak, reads the target's reply, and rewrites it, often succeeding within twenty tries.
- **[garak](https://github.com/NVIDIA/garak)** (NVIDIA) is an open-source scanner. It sends a library of known probes to a model and reports which got through.
- **[PyRIT](https://github.com/Azure/PyRIT)** (Microsoft) is an open-source framework for building automated attacks: it sends prompts, runs multi-turn attacker models, and scores the replies.

An attacker model is untrusted too. Its output must not change the scope, run commands or pick where to send data. And the target's replies can inject the attacker: a document the target reads can contain text aimed at the model attacking it. So the attacker gets back only what it needs, such as "blocked" or "not blocked", and the full trace stays in the private transcript.

## Step 2: define the search before running it

Kiran takes R3's document-to-mail path. The search is written down before it starts:

1. One attacker goal and one legitimate task, both fixed.
2. The surface Mallory controls: the document's text, nothing else.
3. For every candidate: an ID, its parent, the family it came from, and a pointer to the private text.
4. A maximum number of candidates and calls, and a rule for stopping.
5. Attack success, utility and errors as separate fields, scored on state.
6. A discovery set of tasks and a held-out set, split before the search starts.

A small search: three attack families × two places in the document × two document formats = twelve candidates. That is twelve candidates, not twelve samples of one attack's rate. Every candidate is recorded, including the failures. A report that shows only the winner hides how much searching it took.

The winning candidate is then frozen, with its grader, and run on the held-out tasks. That second number is the one a report can use.

## Step 3: the runner

A future adaptive runner would look like this:

```text
load the engagement and a fixed plan
check the target and the attacker model are both in scope
for each candidate, up to the discovery limit:
    write or pick the candidate, through the harness
    restore the target's starting state
    put the candidate only where the plan allows
    record state, utility, errors and the candidate's parent
freeze the winner and the grader
run the held-out evaluation, on its own budget
```

`lab/r0_rates.py` is the fixed-catalogue half of this: four attacks, one task pair, ten runs each. It does no search.

A runner this size makes thousands of calls, so the harness's limits matter more than they did for R0. Two of them are weaker than R1 suggested, and the run below shows it.

## What happened

On 21 October 2026, `python3 r4_harness_checks.py` tested the harness with a stub model, so no API call was made. 4 of 4 checks passed. Two show controls that hold for automation:

- **Generated destinations are refused.** A candidate that points somewhere else is stopped. `https://127.0.0.1:8000`, port 8001, and a hosted address were all refused. So was `http://localhost:8000`, the same FinBot under another name, because scope is matched on the exact scheme, host and port. That is strict, and a tester who types `localhost` gets an error rather than an attack.
- **An attacker model needs a scope change.** A model not listed in `engagement.toml` is refused, so adding one is a recorded decision, not a line in a script.

Two pin down gaps, written so they fail once fixed:

- **The call budget is per process.** Two runs that each load the engagement, with a budget of 3 calls, sent 6 calls between them. Each script starts its own count. Until the harness keeps one shared ledger on disk, a long search split across runs can spend several times the budget, and someone has to add the totals by hand.
- **The token budget can overshoot.** The check runs before each call, against tokens already used. With a budget of 100 tokens, one call that used 150 went through, and only the next was stopped. The limit is "stop after crossing", not "never cross".

`python3 measurement_checks.py` also passed 9 of 9. It checks the counting R6 relies on: an error is never scored as a success or a refusal, and an unscored run is rejected.

Not run: any attacker-model search, scanner or gradient attack. Each would call a model, and no paid runs have been approved for R3–R8.

## OWASP risks in this note

### LLM01: Prompt Injection

- **Example:** A scanner tries 500 placements of an instruction in one document.
- **Issue:** Many wordings through one entry point can look like broad coverage while email and agent hand-offs go untested. A tuned winner can look like a rate.
- **Fix:** Map every candidate to a boundary from R2's plan, and measure only frozen candidates on held-out tasks.

### LLM06: Unbounded Consumption

- **Example:** A search is split across three scripts, each starting its own call count.
- **Issue:** The red team spends three times the agreed budget, and nothing stops it.
- **Fix:** One shared ledger for the whole engagement, checked before every call, and a spending limit on the provider project as the backstop.

### ASI02: Tool Misuse and Exploitation

- **Example:** An attacker model's candidate includes a new address for the target's mail tool.
- **Issue:** Generated text could become permission to contact another system.
- **Fix:** Enforce scope in code outside both models, and grade what the tools did, not what the generated text asked for.

## Problem and next step

**Problem:** a search that scores single replies misses chains. A safe first reply says little about a payment three tool calls later, and an agent that claims success may have done nothing.

**Next, in [R5. Red Teaming Agents](R5.%20Red%20Teaming%20Agents.md):** follow the chain, tell requested actions from blocked and executed ones, and test what happens at each hand-off.
