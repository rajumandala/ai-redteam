# R4. Automated Attacks

R3 turns a threat-model row into a manual experiment. But one tester cannot explore every wording, document layout and tool result. Automation repeats that search. It can also repeat the same mistake thousands of times.

## The idea

Separate **discovery**, where the tester changes attacks after seeing results, from **evaluation**, where a fixed attack is tested on fresh cases. Discovery finds candidates. Evaluation estimates how well those candidates work. A discovery score is not a measured deployment rate.

A scanner is a programme that runs a collection of tests. An attacker model is a language model asked to propose or revise candidates. Neither replaces the rules of engagement or the state grader: the code that checks whether an unauthorised action happened.

## Step 1: choose what to automate

| Method | What changes | What access it needs | Main limit |
|---|---|---|---|
| Fixed catalogue | Known attack families and placements | Approved application inputs | Misses unfamiliar paths |
| Attacker-model search | Wording revised using feedback | An approved attacker model and target | Costs calls; can overfit feedback |
| Gradient search | Token choices optimised against a loss | A local model's weights and derivatives | Transfer to another model or application is uncertain |
| Workflow scanner | Inputs, tool results and conversation steps | A target adapter and state observers | Can test a route the deployed app never exposes |

A **gradient** measures how a model's loss changes with its internal inputs. A loss is a numerical objective, such as making a target continuation more likely. Methods such as Greedy Coordinate Gradient search for token substitutions using those derivatives. A closed model API normally does not expose them. This course therefore explains gradient attacks but does not pretend to run them against the configured API model. An open-model experiment would need separately approved scope, resources and model provenance.

An attacker model needs its own authorisation and budget too. Its suggestions are untrusted data: they must not alter scope, execute commands, install packages or choose outbound destinations. The existing engagement lists only the target model; adding another model requires a deliberate scope change, not a hard-coded bypass.

## Step 2: define the search before running it

Kiran starts with R2's document-to-action path. The search record needs:

1. A fixed attacker goal and a legitimate user task.
2. The surface Mallory controls: document body, not system instructions or arbitrary environment state.
3. A candidate identifier, parent candidate, mutation family and private payload reference.
4. A maximum number of candidates and target calls, plus a stopping rule.
5. State-based success, legitimate-task utility and errors as separate fields.
6. A discovery set and a held-out evaluation set, kept separate before search starts.

For a small search, use a predeclared matrix: three attack families, two document positions and two synthetic document formats. That is twelve candidates, not twelve independent samples of a general attack rate. Hold the user's task and initial state fixed while comparing candidates. Later test the frozen winner on new task pairs. Record every candidate, including failures; reporting only the winner hides the search effort.

No working payload belongs in this note. The family describes a mechanism, such as claimed authority or an instruction hidden inside ordinary task data. The actual text belongs in the private transcript.

## Step 3: fit the target adapter to the question

AgentDojo supplies simulated tasks and grades the final environment. The existing [R0 runner](../lab/r0_rates.py) already repeats a fixed catalogue on one banking task pair. It is a starting point for repeatable evaluation, not an adaptive attacker or a general-purpose scanner.

A future adaptive runner should follow this sequence:

```text
load authorisation and fixed manifest
check target and attacker-model scope
for each candidate within the discovery limit:
    generate or select candidate through the authorised harness
    restore the target's initial state
    test only the permitted injection surface through the harness
    record state grades, utility, errors and candidate lineage privately
freeze candidate and grader
run a separately budgeted held-out evaluation
```

This is a design, not an implemented command. All calls must share one budget ledger; starting another process must not silently reset the engagement allowance. The present harness counters are per object and per process. Until a persistent ledger exists, a single operator must keep an aggregate tally and stop at the engagement limit. Its token guard checks usage before the next call; it is not a hard reservation that prevents the last response overshooting the token limit.

Do not feed unrestricted target replies back to an attacker with tool access. A target document can inject the attacker too. Return only the minimum structured feedback required, with raw traces retained privately.

## Step 4: test the measurement plumbing for free

Automation needs reliable counts before expensive experiments. Run:

```bash
cd lab
python measurement_checks.py
```

The [free exercise](../lab/measurement_checks.py) uses authored outcome records, not generated attacks. It checks that an error is not silently scored as a successful attack or as a completed refusal, and that a missing grade is rejected. It also checks the uncertainty calculations used in R6. No API client, key or target is needed.

For a real scanner, add integration checks: rejected scope produces zero calls; STOP halts both attacker and target loops; each candidate starts from fresh state; a known synthetic state change is detected; harmless text does not count as success; tool requests blocked by enforcement remain distinguishable from executed actions.

## What happened

On 21 October 2026, this continuation was restricted to no paid calls. The existing R0 runner and engagement harness were reviewed, and a standard-library-only measurement exercise was added. Its actual test result is recorded in R6 after execution.

No new AgentDojo attack was run. No attacker model, gradient search or scanner was executed. There is no new success rate, winner or coverage claim. R0's historical fixed-catalogue results remain the only model experiment available here; their zero legitimate-task utility prevents treating them as evidence of a useful secure agent.

## OWASP risks in this note

### LLM01: Prompt Injection

- **Example:** A scanner varies the placement of attacker-controlled instructions inside a document.
- **Issue:** Trying many wordings of one surface can look like broad coverage while missing email and agent hand-offs.
- **Fix:** Map candidates to threat-model boundaries and keep held-out tasks separate from search feedback.

### ASI02: Tool Misuse and Exploitation

- **Example:** An attacker-model suggestion includes a new tool destination.
- **Issue:** A search programme could turn generated text into authority to contact another system.
- **Fix:** Enforce scope in code outside both models. Grade actual actions, not generated tool-call text.

## Problem and next step

**Problem:** a single input/output test can miss a chain across several agents and tools. A safe first reply says little about a later payment or message.

**Next, in [R5. Red Teaming Agents](R5.%20Red%20teaming%20agents.md):** follow the chain, distinguish requested actions from executed effects, and test what happens at tool and agent hand-offs.
